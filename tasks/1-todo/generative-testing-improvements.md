We generate valid typed LIR trees against a generated or fixed schema, then run each query through both implementations:

```text
same schema + same rows + same LIR
                 │
        ┌────────┴────────┐
        ▼                 ▼
 reference interpreter   real Rad
        │                 │
        └──── compare ────┘
```

## Start from a known schema

You could use the existing shop schema:

```text
customers
  id: int
  name: string
  region: string?

orders
  id: int
  customer_id: int
  total: int
  status: string?
```

The generator knows:

- which tables exist;
- which columns belong to each table;
- each column’s type and nullability;
- primary and foreign keys;
- what scopes are currently available.

It can then construct valid queries from the leaves upward.

## Generate relation trees recursively

Conceptually:

```go
func genRelation(
    rng *rand.Rand,
    catalog Catalog,
    depth int,
) GeneratedRelation
```

A `GeneratedRelation` contains both the node and its inferred output:

```go
type GeneratedRelation struct {
    Node   protocol.Node
    Output Schema
}
```

At depth zero, choose a leaf:

```text
scan customers
scan orders
rows [...]
ref binding
```

At greater depth, choose either a leaf or an operator:

```text
scan
filter
project
join
aggregate
distinct
order
slice
```

For example, it might randomly build:

```text
slice
└── order
    └── project
        └── filter
            └── scan orders
```

Or:

```text
aggregate
└── join
    ├── scan customers
    └── filter
        └── scan orders
```

Every time it adds an operator, it uses the child relation’s output schema to make the operator valid.

## Expressions are generated by requested type

This is the key trick.

Instead of:

```go
genRandomExpr()
```

you write something like:

```go
genExpr(env, WantBool)
genExpr(env, WantInt64)
genExpr(env, WantString)
```

To generate a filter predicate, ask for a boolean expression:

```go
predicate := genExpr(input.Output, BoolType)
```

The generator can choose:

```text
eq(integer column, integer literal)
gt(integer column, integer expression)
eq(string column, string literal)
and(boolean expression, boolean expression)
is_null(nullable expression)
```

It cannot accidentally produce:

```text
orders.total + customers.name
```

because the types do not permit that.

Similarly, a projected integer expression could be:

```text
orders.total
orders.total + 10
orders.total * 2
NULL
```

depending on Rad’s typing rules.

## Joins need compatible columns

Given two generated inputs:

```go
left := genRelation(...)
right := genRelation(...)
```

the generator examines their schemas and finds compatible pairs:

```text
left.customer_id : int
right.id         : int
```

Then it builds:

```json
{
  "kind": "join",
  "left": "...",
  "right": "...",
  "on": {
    "kind": "binary",
    "op": "eq",
    "left": { "kind": "column", "scope": "o", "name": "customer_id" },
    "right": { "kind": "column", "scope": "c", "name": "id" }
  }
}
```

It can also deliberately generate:

- equality joins;
- inequality joins;
- composite predicates;
- joins that match nothing;
- many-to-many joins;
- self-joins;
- nullable join keys.

Foreign keys give it likely meaningful joins, but it should not exclusively use them. Arbitrary type-compatible joins are valid and often find stranger bugs.

## You control query complexity with a budget

Rather than only using depth, give generation a complexity budget:

```go
genRelation(budget int)
```

Each node consumes part of it:

```text
scan       1
filter     2
project    2
join       4
aggregate  4
binding    5
```

That prevents enormous accidental trees while still producing varied shapes.

You can weight the choices:

```go
switch weightedChoice(rng, []choice{
    {Scan, 20},
    {Filter, 20},
    {Project, 20},
    {Join, 15},
    {Aggregate, 10},
    {Order, 5},
    {Slice, 5},
    {Binding, 5},
}) {
```

Initially, keep queries small—perhaps 3–8 nodes. Tiny queries are better at producing understandable failures.

## Generate data too

The same system can generate small datasets:

```text
0–4 tables
1–5 columns each
0–20 rows per table
```

Values should be biased toward interesting cases rather than uniformly random:

```text
NULL
0
1
-1
minimum/maximum integers
empty string
duplicate values
repeated foreign keys
missing foreign-key matches
```

For database testing, a table with six carefully distributed values is often more useful than one with a thousand random values.

A generated case becomes:

```go
type Case struct {
    Catalog Catalog
    Rows    map[TableID][]Row
    Query   lir.Query
    Seed    uint64
}
```

The harness loads `Rows` into:

1. the oracle’s in-memory tables;
2. the actual Rad database backed by SlateDB.

Then it executes `Query` through each path.

## Result comparison needs semantics-aware normalisation

You cannot always naïvely compare arrays.

Without an explicit ordering:

```text
[a, b, c]
```

and:

```text
[c, a, b]
```

represent the same relational result.

So comparison depends on the query:

- ordered result: compare row sequence exactly;
- unordered result: compare as a multiset;
- duplicates matter unless `distinct` was applied;
- objects should compare by field identity, not map iteration order;
- NULL must compare according to result equality, not predicate equality;
- errors should compare by stable Rad problem code, not message strings.

A multiset comparison might canonicalise each row and count occurrences:

```go
map[CanonicalRow]int
```

That catches duplicate-count differences while ignoring output order.

## A generated example

The generator could produce something equivalent to:

```text
scan orders as o
→ filter o.total > 100
→ join customers as c on o.customer_id = c.id
→ group by c.region
→ count as order_count
→ order by order_count descending
→ first 3
```

Nobody manually selected that exact shape. On the next iteration it might produce:

```text
scan orders as o
→ project customer_id, total * 2 as doubled
→ filter doubled <= 50
→ self-join on customer_id
```

Then:

```text
binding x = aggregate orders by customer_id
root = join ref(x) as a with ref(x) as b
```

Thousands of structurally different queries emerge from a relatively small grammar.

## Metamorphic generation gives each query more value

Once it generates a valid query `Q`, it can derive related queries whose relationship is known.

For example:

```text
Q
```

and:

```text
filter(Q, true)
```

must produce the same result.

Or:

```text
filter(filter(Q, p), q)
```

versus:

```text
filter(Q, p AND q)
```

Or for a binding:

```text
bindings:
  x = Q

root:
  ref x
```

versus the original `Q`.

So one generated seed query can produce several oracle checks without knowing its exact result beforehand.

This becomes especially powerful for the optimiser:

```text
Q
optimise(Q)
```

Both should mean the same thing according to the interpreter.

## Shrinking turns chaos into regression fixtures

Suppose seed `8291741` generates:

```text
four tables
36 rows
three joins
two bindings
an aggregate
nested boolean expressions
```

and Rad disagrees with the interpreter.

The shrinker repeatedly tries simplifications while retaining the failure:

```text
remove a row
remove a column
replace join input with scan
remove a filter
replace expression with a column
replace literal with 0
remove one binding
```

Eventually it may discover the actual minimal bug:

```text
table t:
  x
  NULL
  1

query:
  filter t where NOT(x = 1)
```

That tiny case is then saved as a permanent handwritten-style conformance fixture.

So generated testing does not replace your 147 cases. It mines new cases for you.

## I’d implement it in this order

First, keep the existing shop schema and rows fixed. Generate only small, valid LIR queries against it. This isolates query-shape bugs without schema/data generation adding noise.

Then add:

1. random row populations for the fixed schema;
2. schema generation;
3. bindings and self-joins;
4. metamorphic transformations;
5. shrinking;
6. PIR programs and transaction-state comparison.

The first useful version could be surprisingly small:

```text
fixed shop schema
fixed dataset
scan/filter/project/join
typed expression generator
1000 deterministic seeds
oracle vs Rad result comparison
```

That alone would cover vastly more combinations than humans—or AI agents—would reasonably enumerate as fixtures. AI-written fixtures give you broad intentional examples; generation systematically explores weird compositions that neither you nor the AI thought to request.
