# Distinct relations and recursive accumulation

Status: **implemented** (2026-07-17), companion to recursive bindings
(`tasks/2-building/recursive-queries.md`). The naming is settled: `accumulation:
all | new` is the recursive fixpoint admission policy; `distinct` is the unary
relation operator; the two share one canonical full-row identity
(`bound.CanonicalRowSet`). The `union: all | distinct` wire fallback weighed
below was **not** taken — `accumulation: all | new` reads as the recursive
semantic it is and never appears to invoke the unary operator.

What landed, layer by layer: the wire `RecursiveBinding.union` field became
`accumulation: [all, new]` and a `DistinctNode` (`kind: distinct`) joined the
`Node` union (`rad/protocol/lir.schema.yaml`, regenerated `lirwire`); the unbound
IR gained `lir.Distinct` and `lir.RecursiveAccumulationMode` (`AccumulateAll` /
`AccumulateNew`), replacing the earlier `Distinct bool`; the shared
`bound.CanonicalRowSet` (NULL == NULL, type- and order-significant full-row
identity) was extracted from the recursive seen-set and now backs both admit-new
accumulation and the `distinct` operator; the bound IR grew `bound.Distinct`
(complete-row-is-unique-key metadata), the planner `DistinctExec`, the executor
`distinctOp` (blocking), and the `refexec` oracle a matching case; EXPLAIN prints
`accumulation=<mode>` and a `Distinct` node. Tests:
`tests/planner/distinct_test.go` (eight cases through the real
client→server→engine path, including the cross-feature check that `distinct` and
recursive admit-new agree over one bag) and
`rad/engine/03_lir/bound/rowset_test.go` (the shared identity primitive). The
ordinary and generative differential suites are green.

## Goal

Complete the current recursion phase by introducing a general-purpose relational
deduplication operator and by clarifying the terminology around the several
independent places where duplicate handling appears.

The objective is not to reproduce SQL's overloaded use of `DISTINCT`. Rad should
model each operation according to its actual relational role, while sharing one
canonical definition of row identity underneath.

This phase therefore delivers two related but distinct features:

1. recursively defined bindings with explicit accumulation semantics;
2. a unary `distinct` relation operator applicable to any relation.

## Naming decision

Keep the relation operator name **`distinct`**.

Do not rename it to `unique`.

`unique` already denotes a different database concept: a key, index, or
constraint guaranteeing that particular column values do not repeat in stored or
derived data. A `distinct` operator instead consumes a bag relation and produces
the corresponding set of complete rows.

The vocabulary should remain:

* **`project`** — derive a new row shape;
* **`distinct`** — remove duplicate complete rows from a relation;
* **unique key / unique index** — a static integrity or cardinality property;
* **recursive accumulation mode** — control how rows generated by recursive
  iterations enter the fixpoint result.

`project` intentionally replaces SQL's misleading `select`, but `distinct` is
already the established relational term and is less ambiguous here than `unique`.

## Separate the concepts explicitly

The implementation and specification should distinguish four duplicate-related
concepts.

### 1. Relation distinctness

A unary logical operator:

```text
Distinct(input) -> relation
```

It removes duplicate complete rows from an arbitrary input relation.

SQL:

```sql
SELECT DISTINCT author_id
FROM posts
```

lowers to:

```text
scan
→ project author_id
→ distinct
```

Distinctness applies after projection and therefore compares the complete
projected row.

### 2. Recursive accumulation

A recursive binding repeatedly evaluates its step against the current frontier
and accumulates generated rows.

This is not the unary `distinct` operator.

Its internal mode should be named around recursive accumulation, for example:

```go
type RecursiveAccumulationMode uint8

const (
    RecursiveAccumulateAll RecursiveAccumulationMode = iota
    RecursiveAccumulateNew
)
```

Suggested wire wording:

```yaml
accumulation: [all, new]
```

Semantics:

* `all` — every generated row enters the result and next frontier;
* `new` — only rows not already admitted to the recursive result enter the
  result and next frontier.

`new` describes the actual fixpoint behaviour more clearly than recursive `union
distinct`: admit only newly discovered full rows.

This also prevents the recursive binding from appearing to invoke the unary
`distinct` operator.

If compatibility or familiarity favours retaining the current wire shape:

```yaml
union: [all, distinct]
```

then the specification and internal types should still consistently call it
**recursive accumulation** rather than general distinctness.

### 3. General set operations

Future operators may include:

```text
Union(left, right, mode)
Intersect(left, right, mode)
Except(left, right, mode)
```

Their duplicate modes belong to set-operation semantics and should use their own
enum type rather than reuse recursive accumulation types.

### 4. Aggregate input deduplication

A future construct such as:

```sql
COUNT(DISTINCT user_id)
```

deduplicates the values entering one aggregate term. It is neither relation
distinctness nor recursive accumulation and should be represented independently
if introduced.

## Shared semantic foundation: row identity

All duplicate-sensitive operations should share one canonical definition of
full-row identity.

This identity is not predicate equality.

Required semantics:

* comparison covers the complete row;
* column order and type are significant;
* `NULL` equals `NULL`;
* duplicate structural values compare structurally once those values are
  supported;
* equality is stable across physical plans and storage encodings.

Introduce or extract a neutral reusable primitive such as:

```go
type CanonicalRowSet struct {
    // canonical tuple identity -> membership
}

func (s *CanonicalRowSet) Add(row Row) (inserted bool)
func (s *CanonicalRowSet) Contains(row Row) bool
```

Avoid naming the shared primitive `DistinctSet`, because it implements row
identity membership rather than any one logical operator.

Expected consumers:

* `DistinctExec`;
* recursive `new` accumulation;
* future `UnionDistinctExec`;
* future `IntersectExec`;
* future `ExceptExec`.

The same canonical tuple encoding currently used by recursive accumulation
should become the shared implementation of this rule.

## New logical operator

Add a unary relation node:

```yaml
DistinctNode:
  type: object
  additionalProperties: false
  required: [kind, input]
  properties:
    kind:
      type: string
      const: distinct
    input:
      type: string
      minLength: 1
```

Add it to the `Node` union.

Normative description:

> Remove duplicate complete rows from `input`. Two rows are duplicates when
> every corresponding datum has the same canonical row identity; typed NULL
> values compare equal for this purpose. The output has the same row type as the
> input and contains at most one occurrence of each complete row. `distinct`
> determines membership and multiplicity, not order. Any observable output
> ordering requires an explicit `order` above it.

## Bound semantics and metadata

`distinct` preserves:

* output columns;
* output kinds;
* output nullability;
* visible scopes or an explicitly rebound output scope, according to existing
  pass-through-node conventions.

It changes:

* multiplicity;
* cardinality estimates;
* key metadata.

After `distinct`, the complete output row is a unique key.

It does not imply that any individual column or proper subset of columns is
unique.

The planner may use this complete-row uniqueness for:

* cardinality reasoning;
* redundant distinct elimination;
* later determinism proofs where relevant.

## Ordering semantics

`distinct` should not promise stable first-occurrence preservation.

The logical result has no ordering guarantee merely because its input was
ordered.

Canonical usage:

```text
project
→ distinct
→ order
```

This permits either hash-based or sort-based physical implementations and
prevents physical encounter order from leaking into results.

Potential optimizer laws:

```text
Distinct(Distinct(x)) = Distinct(x)
```

```text
Distinct(x) = x
```

when the planner can prove the complete row is already unique.

Order should not automatically commute through `distinct` unless a later
optimizer proves the transformation preserves the requested semantics.

## Planner

Introduce a physical distinct operator, initially blocking:

```text
DistinctExec
  input
```

Planning steps:

1. plan the input;
2. preserve its canonical output slot layout;
3. create a `DistinctExec`;
4. mark the complete output row as unique;
5. discard logical ordering guarantees unless explicitly re-established above.

A later optimizer may select between:

* hash distinct;
* sort distinct;
* streaming distinct when input uniqueness or compatible ordering proves it safe.

The first implementation should use the simplest correctness-first strategy.

## Executor

Initial algorithm:

```text
seen := CanonicalRowSet
drain input
for each row:
    if seen.Add(row):
        emit or buffer row
```

Because the operator makes no ordering promise, emission may occur immediately
on first canonical occurrence or after complete materialisation. The logical
contract must not depend on that choice.

The recursive executor should be refactored to use the same `CanonicalRowSet`
when operating in admit-new mode.

For each recursive iteration:

```text
next := empty frontier

for each generated row:
    if accumulation == all:
        append to result
        append to next
    else if globalSeen.Add(row):
        append to result
        append to next
```

Updating the global seen set row-by-row also removes duplicates generated within
the same iteration.

## Reference interpreter

Add the corresponding unary operation to `refexec` using the same normative
identity semantics.

The physical executor and reference interpreter need not share code, but they
must agree on:

* full-row equality;
* typed NULL identity;
* duplicate removal;
* output multiplicity.

Recursive accumulation remains independently represented in the interpreter,
while using the same semantic definition.

## Wire and IR naming

Recommended names by layer:

```text
Wire/LIR:
  DistinctNode
  kind: distinct

Recursive binding:
  RecursiveAccumulationMode
  AccumulateAll
  AccumulateNew
```

If the existing recursive wire field remains:

```yaml
union: all | distinct
```

use explicit internal names:

```go
type RecursiveUnionMode uint8

const (
    RecursiveUnionAll RecursiveUnionMode = iota
    RecursiveUnionDistinct
)
```

Do not use:

```go
Distinct bool
```

A boolean obscures which distinctness concept it represents and encourages
accidental coupling to the unary operator.

## Required tests

### Relation distinct

* duplicate scalar rows collapse;
* already unique input remains unchanged;
* all-identical rows produce one row;
* empty input stays empty;
* typed NULL rows deduplicate with `NULL == NULL`;
* rows differing only by one column remain distinct;
* rows with different scalar kinds remain distinct;
* projection followed by distinct matches `SELECT DISTINCT` semantics;
* distinct followed by explicit order is deterministic;
* distinct does not claim to preserve input order;
* double distinct is idempotent;
* complete-row uniqueness metadata is produced;
* downstream ref/project/join/aggregate can consume the result normally.

### Recursive accumulation

* diamond graph admits the shared node once under admit-new mode;
* diamond graph admits both derivations under all mode;
* duplicates generated within one iteration are removed under admit-new mode;
* duplicates generated in a later iteration are removed against the global seen
  set;
* typed NULL rows use the same identity as unary distinct;
* growing state such as depth makes revisits distinct full rows;
* accumulated-row caps remain independent of relation distinct semantics.

### Cross-feature consistency

Given the same bag of generated rows:

```text
Distinct(rows)
```

and recursive admit-new accumulation should agree on canonical row identity.

This should be tested with a shared fixture table covering:

* text;
* int64;
* float64;
* bool;
* typed NULL;
* multi-column rows.

## Non-goals

This phase does not require:

* binary `union`;
* `intersect`;
* `except`;
* aggregate-level distinct inputs;
* structural array equality beyond the currently supported value domain;
* stable-distinct ordering;
* SQL frontend syntax.

These can reuse the same row-identity foundation later.

## Documentation updates

Update the recursive ADR to say:

> Recursive accumulation and the unary `distinct` relation operator are separate
> logical concepts. Recursive admit-new accumulation incrementally rejects rows
> already present in the fixpoint result; `distinct` deduplicates one completed
> arbitrary relation. They share canonical full-row identity but remain different
> LIR constructs and planner operations.

Add to the LIR model:

> Relations have bag semantics unless an operator explicitly changes
> multiplicity. The `distinct` operator converts an input bag into the
> corresponding set of complete rows.

Add to the determinism section:

> `distinct` imposes no logical ordering. An observable ordered distinct result
> requires an explicit `order` above it.

## Acceptance criteria

This work is complete when:

* `distinct` exists as a first-class unary relation operator across wire, unbound
  LIR, bound LIR, binder, planner, executor, reference interpreter, EXPLAIN, and
  tests;
* recursive accumulation uses the shared canonical row-identity abstraction;
* the code uses separate, concept-specific types for relation distinctness and
  recursive accumulation;
* NULL identity is consistent across both features;
* the complete output row is exposed as a unique planner key after `distinct`;
* documentation no longer relies on SQL's overloaded use of the word `DISTINCT`;
* the full ordinary and generative differential suites remain green.
